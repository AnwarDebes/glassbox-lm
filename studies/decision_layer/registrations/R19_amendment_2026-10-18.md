## Wording correction (2026-10-18, after the runs)

The registration's "Reported with no rule" list (line 85 of the text as registered) says: "This task has 30 buttons, not the 231 button-slot options of the ABCD paper's B-Slot, so it is not comparable with the paper's 89.9 / 93.6." **That is wrong.**
- The paper's released code (asappresearch/abcd, read in `data/untrusted/abcd/code`, not run) scores B-Slot as the choice among the 30 buttons:
  - `prepare_action_labels` builds the label set from the ontology's 30 buttons;
  - `action_to_id` drops the slot position ("verify-identity a" becomes "verify-identity");
  - `ast_report` scores the argmax over the buttons on every AST example.
- The paper's README also says 30 options. Only its Sec. 6.3 says "231 known options"; 231 is the paper's count of slots.
- So the AST-weighted accuracy (`ast_bslot_bert`, the paper's example filter ported in `scripts/abcd_prepare.py`) is the paper's B-Slot accuracy on its test examples. The study's R9 section already used it that way.
- The frozen file is unchanged. `docs/results.md` (R19) and `FAILURE_MAP.md` (Part 12) carry the corrected reading:
  - the word-table agent scores 84.78 (BERT's filter) / 84.82 (RoBERTa's);
  - published (Table 3): the pipeline BERT 86.7, BERT 89.9, AlBERT 90.9, RoBERTa 93.6;
  - the agent is 1.9 to 8.8 points behind them, with no parity claim.
- Found after the runs, from the paper's code, and confirmed independently.

## Post-hoc LR refit at the dev-best C (rules written 2026-10-18T20:25:28Z, before e67b's numbers)

e67 (dev, post hoc) found STAR's LR on view B still rising below the registered grid: C 0.1 gives 0.6409, 0.03 gives 0.6501, 0.01 gives 0.6555. A known under-tuned baseline flatters the TM, so the LR baseline is refit under these rules, fixed now. No registered rule involves LR, so no verdict can change.

1. **Choosing C, on dev only.** Take the best of {0.1, 0.03, 0.01, 0.003, 0.001} by dev accuracy, with ties going to the larger C.
   - The values below 0.01 are run for both datasets (e67b for STAR, e67c for ABCD), so the rule is applied the same way to each.
   - If the best is 0.001, the new edge of the grid, that is said, and the search stops there.
2. **When to refit.** A dataset is refit only if its dev-best C beats C 0.1 by at least 0.5 points on dev.
   - Otherwise its test split is not read again, and "may favour the TM" stays in the write-up for that dataset.
3. **The refit.**
   - One LR fit on train at that C, followed by one test read.
   - Same view and bits as R19: STAR train a3ce2dd9, dev bc27a3c6, test bc78ca9c; ABCD train 1f81cb23, dev 2f3223b2, test b7bad9ae. These are checked by the script.
   - Same code path as abcd_confirm.py's lr arm (`dl.linear.fit_logreg`, `logits`), seed 0.
   - New script: `scripts/lr_refit_posthoc.py`. Output: `results/confirm/<R19star|R19abcd>/lr_mem_static_posthocC/`.
4. **Scoring.** The registered report's statistic (`scripts/report_abcd.py`; bootstrap over dialogues, 10,000 resamples, seed 0) on two pairs:
   - TM static minus the tuned LR;
   - the tuned LR minus the bge-large LR.
5. **bge-large's LR is not refit.** Its dev checks put C 0.1 within 0.1 point of the best:
   - R18: C 0.03 is +0.1 and C 0.01 is -2.0;
   - R9b (e41): the peak is at C 0.1.
6. **Counted as a use of the test split.**
   - STAR: this is the 3rd use (after R18 and R19), so R20 becomes the 4th.
   - ABCD, if refit: its 12th, so R20 becomes its 13th.
   - Every number is labelled "post hoc, no rule, LR baseline refit at the dev-best C, after the registered runs", and the full dev C curve of both datasets is given next to it.
7. **Wording.**
   - If the gap grows, it is written plainly ("on the table's bits the TM is X points behind a tuned LR on STAR").
   - "May favour the TM" is dropped for a dataset once its number exists.
