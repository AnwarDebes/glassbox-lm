# A2 registration: which category code helps the count floor

**Status: frozen 2026-10-25T13:38:45Z** with `scripts/freeze.py` and the extra files listed under "Pins" (record
`A2.frozen.json`). Written on 2026-10-25 from 13:28 UTC in the finish pass of the study, after two rounds of read-only
review (judged by AI models, not people; the first round found one blocker and ten majors, the second seven majors and
27 minors). Every point was answered and the script changes they asked for were made and tested. `scripts/a2_run.py`
refuses the dev-test look without a freeze record that matches every pinned file. Changes after freezing are dated
amendments in a new file. This published copy leaves out the draft history and is edited in wording only; the
registered text's SHA-256 is in `docs/hash-table.md`.

Line A of the design (`research/design.md`, step A2, "the CDE test"). **Wording rule: A2 has no
Tsetlin part, except that one candidate code, `orgroups`, is taken from the OR-groups of a
Hierarchical Tsetlin Machine run of the hierarchical_tm study.** A result of A2 is a result about
count models with category codes. Only the `orgroups` arm says anything about a code derived from a
Tsetlin Machine, and only about that code; no outcome of A2 is to be described as a test of
Tsetlin learning.

## Question

On Penn Treebank next-word prediction, does a Kneser-Ney 5-gram model with a cache, the count floor
without classes, get at least 5% lower perplexity on the dev-test split when the class members of
the exchange code are mixed in, and is that code ahead of random codes with the same class sizes?
The other candidate codes are measured on the same footing and reported without a verdict.

## Data and splits

- Penn Treebank, Mikolov preprocessing, V = 10,000 including `<unk>` and `<eos>`, the splits of
  `src/tally/ptb.py` (the same as T0): blocks of 100 sentences of the standard training file,
  permutation seed 20261015: train 379 blocks (836,253 tokens), calib 21 blocks (46,925 tokens),
  dev-test 21 blocks (46,411 tokens, as registered for T0); the standard validation file is valid
  (73,760 tokens, 34 blocks). The standard test file is not opened.
- **The splits are blocks of the training file, not documents** (the README's rule 2 asks for
  documents). Articles continue across block edges into train, and 45 dev-test sentences (2.1%, 388
  tokens) also occur verbatim in train (results page, findings of the reviews of T0). Valid is a
  separate file.
- **The vocabulary is not built from train only.** It is the fixed Mikolov list, built from the whole
  training file, dev-test blocks included, as for T0 and A1: 8 of its words occur only in dev-test
  (63 positions, results page), and 18 have no train count (`topic.json`, key `zero_count_words`); 10
  of these 18 occur in calib and 2 in valid (13 valid positions). This departs from rule 3 (everything
  built from text comes from train or calib). Unlike in T0, where the unigram over these words was the
  same in every arm, the codes place them differently (read from the saved codes on train counts,
  2026-10-25): the exchange code puts all 18 into one class at every level (45 words at the
  1,024-class level); the topic code into one class per level; `kmeans200` and `orgroups` give each its
  own class; the predefined code tags them by spelling (one part-of-speech class, 5 classes at the

## The system and the arms

Every arm is KN5 + cache + the class members of one code (`scripts/a2_run.py`, docstring):

- KN5: interpolated modified Kneser-Ney 5-gram, counts from train, sentence mode
  (`src/tally/floor/kn.py`; matched to KenLM on valid within 3.8e-5 in perplexity, A1).
- Cache: decayed unigram cache, reset at every 100-sentence block (`src/tally/floor/cache.py`);
  half-life and whether `<eos>` is added are chosen on valid without class members (grid of 18
  settings in `a2_run.py`), and kept for every arm. The development runs chose half-life 100 with
  `<eos>` skipped.
- Class member: a class 5-gram (interpolated modified Kneser-Ney on the class stream, sentence
  mode) times P(w | class) with add-0.5 emission (`src/tally/floor/classlm.py`), one member per
  level of the code.
- Mixing: linear interpolation, one global weight set per arm fitted by EM on calib
  (`src/tally/floor/mix.py`).

Arms (codes built from train by `src/tally/floor/codes.py`; class counts per level as built by the
development run, `metrics.json`, key `codes`):

| Arm | Members | What it is |
|---|---|---|
| `none` (the comparator) | 0 | KN5 + cache |
| **`exchange` (claim-carrying)** | 4 | exchange tree (Martin, Liermann and Ney 1998) at 1024 classes, merged into 256, 64, 16 (17, 65, 257, 1,025 classes with `<eos>`) |
| `random_s1` to `random_s10` (the control) | 4 each | the exchange tree with the words permuted, seeds 1 to 10; every level keeps the class-size distribution |
| `kmeans200` | 1 | k-means-200 recipe of clause_lm on train (9,201 classes) |
| `predefined` | 2 | part of speech (perceptron tagger trained on Brown), then part of speech plus the WordNet 3.0 supersense of the first synset (13 and 58 classes); reported as noisy, as the longer design document's row A2 asks |
| `topic` | 2 | sliding-window code, k-means 256 then 64 (65 and 257 classes) |
| `kind_topic` | 6 | the exchange and the topic members together |
| `orgroups` | 1 | the OR-groups of the hierarchical_tm run `20261002T050235Z_e4_head_sa_s1_scoreP100` (9,142 classes, of which 9,070 are single words: 930 PTB words in 72 groups) |
| `exchange_level0` to `exchange_level3` | 1 each | one level of the exchange tree alone |

No arm with codes from a Tsetlin Machine auto-encoder is run: the repository holds no saved TM
auto-encoder model and none with a code over the 10,000 words (the tmu auto-encoder runs of
tm_language_model, `20260919T202646Z_p0_tmu_ae_run_seed1`, `20260919T202646Z_p0_tmu_ae_run_seed2` and
`20260919T203409Z_p0_tmu_ae_run_seed3`, the last recorded as running, used 200 target words each
(`config.json`, key `n_targets`) and saved no model file).

**The claim-carrying code is `exchange`, named here before the dev-test look and fixed in the script
(`CLAIM_ARM`).** How it was named, after the development run on valid, said plainly: the script's
development rule (the candidate with the lowest valid perplexity) picks `kind_topic` (122.1502478),
2e-7 below `exchange` (122.1502480, 1.6e-9 relative); EM on calib gave both topic members of
`kind_topic` weights below 5e-6 (0.0 to five decimals), so the two arms are in practice the same
system, and the topic code added nothing on calib or valid. This registration departs from the
script's rule and breaks the tie by the fewer members: `exchange`. The departure cannot in practice
change the verdict.

## Metric, statistic and verdict lines

- Bits per token and perplexity on dev-test over the full distribution over V, `<eos>` counted.
- gain = 1 - ppl(exchange) / ppl(none); margin = 1 - ppl(exchange) / (arithmetic mean of the ppl of
  the 10 random codes); the paired per-token difference bits(exchange) - bits(random mean), where the
  random mean is the per-token mean of the natural log probabilities of the 10 random arms (a
  geometric mean in perplexity; on valid the two random means differ by 1.1e-10 relative, so they
  cannot disagree on any line), with a 95% percentile interval from 1,000 resamples of the 21 dev-test
  blocks (`stats.block_bootstrap`, seed 0, ratio estimator).
- The lines are the ones `scripts/a2_run.py` (sha256 under "Pins") holds:

  ```
  SUCCESS_PPL, KILL_PPL, MARGIN_PPL = 0.05, 0.02, 0.01
  ...
  gain = 1 - R[best]["all"]["ppl"] / base
  marg = 1 - R[best]["all"]["ppl"] / r_ppl.mean()
  bb = stats.block_bootstrap(stats.bits_diff(LP[best], lp_rmean), bv)
  ...
  "success_line": bool(gain >= SUCCESS_PPL and marg >= MARGIN_PPL and bb["hi"] < 0),
  "kill_line": bool(gain < KILL_PPL)}
  ```

  with `best` = `exchange` in the look.
- **When these were fixed.** The three lines, the cache grid, the candidates, class order 5, add-0.5
  emission, the 10 random codes and the bootstrap are in the config of the first smoke run,
  `20261015T074420Z_a2_smoke` (2026-10-15 07:44:20 UTC), before any dev-test number of the study. The
  full code sizes (exchange levels 16/64/256/1024, k-means (1000, 200, 2000), topic (256, 64), 5 tagger
  iterations) are first recorded in commit e9febbd (2026-10-23 11:06:00 UTC); the smoke config holds
  the smoke sizes (4/8/16/32, (200, 20, 400), (32, 8), 1 iteration). That the full sizes were the
  intended ones on 2026-10-15 is UNVERIFIED. T0's dev-test numbers, read before 2026-10-23, concern
  Tsetlin arms and Kneser-Ney and say nothing about code sizes.
- **Success:** gain at least 0.05, margin at least 0.01, and the interval of bits(exchange) -
  bits(random mean) entirely below 0.
- **Kill:** gain under 0.02.
- Otherwise: no claim (between success and kill there is no claim; design rule 1).
- The 5% line is on the point gain. Beside it, with no rule: the interval of the gain over dev-test
  blocks, 1 - 2^hi to 1 - 2^lo from the interval of bits(exchange) - bits(none)
  (`gain_interval_from_bits_vs_none_no_rule`; on valid 7.44% to 8.77%), and an interval that includes
  train-side noise (`gain_interval_train_inclusive_no_rule`, see "Seeds and noise"; on valid 6.10% to
  10.12%).
- **The control is the comparator itself.** On valid and in the calib cross-fit the random arms equal
  `none` to within 0.005%: EM gives their class members weights of at most 0.0024, and the dev-test
  look uses the same weights (fitted on calib). So the margin equals the gain to within 1e-5 (0.001
  percentage points; 4.4e-6 on valid, 1.0e-5 on calib), and the interval against the random mean is in
  effect the interval against `none`: the success line is in effect "gain at least 0.05". "Ahead of the
  random codes" is met because EM switches same-size random classes off; it shows that random classes
  of these sizes add nothing, not that exchange beats a strong control. (A frequency-preserving
  control, words permuted within frequency bands, would be stronger; it is not part of this
  registration.)
- The design page states the line as "Pass: at least 5% better than without classes"; the longer
  design document of the project notes (not published), row A2, as "at least 5% lower perplexity than
  the system without class members and clearly ahead of the random codes; kill: under 2%". The margin
  of 1% and the interval are the script's form of "clearly ahead".
- **Reported with intervals and no verdict:** every other arm against `none` (`bits_diff_vs_none`);
  the arm that is best on dev-test (`best_on_eval_split_no_verdict`; `exchange` and `kind_topic` are in
  practice the same system); `exchange` against `none` and against the random mean on three subsets
  (`subsets_no_verdict`): the positions whose bigram is unseen in train, the positions outside duplicate
  spans (spans of at least 8 tokens that also occur in train, the mask of `stats.duplicate_mask`; not
  the list of 45 verbatim sentences of T0's review), and the positions whose word has a train count
  above 0; KN5 alone (`kn5_alone`); per code SimLex-999, WS-353, the synonym-pair sense test and the
  n-gram growth. A positions-away-from-block-edges subset is not computed (its definition in T0's
  review is not in this study's code). No subset reading overrides the verdict.
- **Expected direction, written before the look:** class members help most where the word context is
  unseen in train (on valid: -0.621 bits per token at unseen-bigram positions, -0.122 on all), and
  articles that continue across block edges and verbatim duplicates raise the share of seen contexts
  and favour the word n-gram member, so the gain on dev-test is expected to be smaller than on separate
  documents; this is conservative for the success line.
- **Multiplicity:** no correction is applied. The one verdict is a conjunction of three conditions
  that must all hold. No other number is a claim: the 19 other arms against `none`, the arm best on
  dev-test, the three subsets, KN5 alone, the two gain intervals and the code reports carry no verdict.

- **If the success line is met**, the claim is worded, with X, a, b, r1, r2 and w read from the look's
  `metrics.json`:

  > "On 21 held-out 100-sentence blocks of the Penn Treebank training file (dev-test; V = 10,000,
  > `<eos>` counted), the class members of an exchange-class code (Martin, Liermann and Ney 1998; 16 to
  > 1,024 classes, counts from train), chosen on valid among six candidate codes before the look,
  > lowered the perplexity of a Kneser-Ney 5-gram with a cache by X% (95% interval over dev-test blocks
  > a% to b%; it does not include train-side noise). This confirms the development result (valid 8.11%,
  > calib cross-fit 7.93%), from which success was predicted before the look; exploratory in the sense
  > of design rule 12 (one build, one split, one benchmark). The 10 random codes with the same class
  > sizes were r1% to r2% from the system without classes (no rule; EM weights of their members at most
  > w)."

- **Always add:** "The gain is of the size of the class-model gain in a 2011 table (125.7 to 115.6,
  8.0%, as quoted on the design page; another evaluation split and other implementations, so not a
  comparison under design rule 8). Dev-test is 21 blocks of 100 sentences of the Penn Treebank
  training file, not separate documents (2.1% of its sentences occur verbatim in train), and the
  vocabulary is the fixed Mikolov list built from the whole training file, dev-test included."
- **Never:** "replicates" for the 2011 table; "at least 5%" unless a% is at least 5%; "the CDE test
  passed"; "category codes help" without "exchange classes"; "kind of word plus topic helps"; "random
  codes add nothing" as a finding (it has no rule); any wording that makes `orgroups` or A2 a Tsetlin
  result.
- If the kill line is met or there is no claim, the same facts are given with the outcome, and the
  prediction is said to have failed.
- **Pre-stated no-verdict readings:** the `orgroups` arm, the one code derived from a Tsetlin Machine,
  added nothing on valid and calib (EM weight 0.0). Its code is close to the identity (9,070 of 9,142
  classes are single words), so its member nearly duplicates the word 5-gram and weight 0 is expected
  by construction: it is reported as a negative reading that is uninformative about Tsetlin-derived
  codes by construction, whatever its dev-test value.

## Seeds and noise

- The arms are deterministic: counts, EM and the bootstrap give the same numbers on every run (the
  second and third development runs reproduced the first exactly). The seeded parts are fixed: random
  codes seeds 1 to 10 (the control, 10 draws as design rule 9 asks), k-means `random_state` 0, SVD
  start vector seed 0, the tagger's `random.seed(0)`, bootstrap seed 0.
- Design rule 9 of the longer design document reads: "Noise first: an A/A run; then paired differences
  with a 95% interval from a document bootstrap; at least 5 independent seeds, 10 for a pass or fail
  claim; 10 draws of every random control. Never 'k of n seeds'." For deterministic arms there are no
  training seeds; A1 defines a repeat as a rebuild without a seeded 5% of the train blocks. The verdict
  rests on one build of each arm (all train blocks), which is one reason the claim is exploratory
  (rule 12, below). The registered interval covers the sampling of dev-test blocks only; it treats the
  train blocks, the EM weights fitted on calib and the 10 random codes as fixed.
- **The spread over 10 rebuilds that each drop a different seeded 5% of the train blocks** (A1's
  repeat; 19 of 379 blocks; the exchange code, KN5, the cache choice and the mixing weights rebuilt from
  the kept blocks), measured before the freeze as dev work: the valid gain of `exchange` over `none` has
  a mean of 0.0827, a standard deviation of 0.0013 and a range of 0.0795 to 0.0840; in the calib
  cross-fit a mean of 0.0825, a standard deviation of 0.0022 and a range of 0.0795 to 0.0859
  (`verification/a2_dev/a2_gain_noise.py` and its output; repeat 0, with every block, gives the
  development run's gain exactly). This is the response to a 5% perturbation of the training set, not
  the sampling SD of a training set of this size.
- **Scaled to a training-set SD (an estimate, UNVERIFIED):** the delete-d jackknife factor
  sqrt((379 - 19) / 19) = 4.35 gives about 0.0057 (valid) and 0.0097 (calib cross-fit) in gain, 0.6 to
  1.0 percentage points (10 subsets, dependent blocks and a non-smooth code builder make this rough).
  The gain would have to move by about 3 points to change the reading; the train-side SD is about 1
  point (estimate).
- **Pre-registered beside the verdict, with no rule:** a train-inclusive interval of the gain,
  gain ± 1.96 sqrt(se_b² + 0.0097²), where se_b = (block-bootstrap SD of bits(exchange) - bits(none)) x
  ln 2 x 2^(mean difference) (the delta method); `a2_run.py` writes it as
  `gain_interval_train_inclusive_no_rule` (constant `TRAIN_SD_GAIN` = 0.0097). On valid it is 6.10% to
  10.12% (third development run). With the 21-block SE it is about 2.5 to 2.8 times as wide as the
  registered interval.
- The A/A runs of A1 (`20261025T113715Z_a1_aa_noise`) found the same caveat for one system's level:
  with 5% of the train blocks dropped, 8 of 45 pairs of repeats have a block interval that excludes 0
  (KN5 + cache: standard deviation 0.30 in valid perplexity, 0.23%).

## What the known numbers predict (no rule)

- **Success is predicted.** The gain was 0.0811 on valid and 0.0793 in the calib cross-fit (EM weights
  fitted on one half of the calib blocks and read on the other, both ways). Calib is cut from the
  training file like dev-test.
- **Power, from calib's own 21 blocks** (`verification/a2_dev/a2_calib_boot.py` and its output): the
  block-bootstrap SD of bits(exchange) - bits(none) on calib is 0.00572 bits (seed 0, 1,000 resamples;
  0.00563 with 10,000), 0.0037 in gain at the line. The 5% line (-0.0740 bits) is 7.9 standard errors
  from the calib value (-0.1192 bits) for the sampling of dev-test alone, and 5.6 with calib's own
  sampling error added (sqrt 2). The gain needed for 80% power at the line is 5.32%. The interval
  against the random mean excludes 0 from a gain of about 0.8% (1.1% for 80% power). (Scaled from
  valid's 34 blocks instead, the SE is 0.00661 bits: 4.8 standard errors with calib's error, 3.9 at the
  rough 0.074 below, and 5.37% for 80% power; 0.89% and 1.28% for the random interval.)
- KN5 alone is easier on dev-test: 7.1760 bits per word there (T0's run beside), 7.2551 on valid,
  7.2986 on calib (A1's A/A repeat 0). If the 0.12 bits by which dev-test is easier than calib came
  entirely from fewer unseen bigrams, the gain would be about 0.074 (a rough estimate, UNVERIFIED). On
  valid the gain would fall to 5% only if the unseen-bigram share fell to 13.8% or less; it is 21.4% on
  calib and on valid. The kill line cannot be reached from these numbers.
- The look therefore checks that the dev gain carries over to 21 untouched blocks, and that the
  dev-test path works. A miss would point to a difference of the split or to a bug, and is reported as
  such. No dev go-bar was fixed before the dev rows existed; a bar written now would be decided by
  those rows, so none is written; the calib cross-fit serves as the power check.
- Selection: the claim code was the best (tied) of six candidates on valid, and the cache was chosen
  on valid; valid is therefore mildly optimistic. The lead over the next candidate (`kmeans200`, gain
  0.0102) is about 7 points, so the winner's bias is negligible; the calib cross-fit is the better
  predictor.

## If the look stops

- **(a) A stop before the first dev-test score** (the code, cache or EM-weight checks; `run.json` shows
  state "stopped" and `eval_scored` false): it is not a use. The folder, the output file and the
  reason are kept and logged; the cause is fixed by a dated amendment that names the folder; the
  amendment renames the folder to `<run id>_a2_look_void` (outside the guard's pattern `*_a2_devtest*`),
  and the look is started once more.
- **(b) A stop or a crash after scoring** (a contract or the future-change test, a crash in the code
  reports or in saving `logp.npz`; `eval_scored` true): it is the same use, and no number is read from
  partial output. The fix is a dated amendment, and the rerun is reported with the stop, both outputs
  shown (rule 12).
- **(c) A recompute mismatch, a KN5-alone value other than 7.1760, or a changed freeze record:** no
  verdict until the cause is found; both numbers are shown.
- A start refused by the guard before the run folder exists (step 1) is not a use.
