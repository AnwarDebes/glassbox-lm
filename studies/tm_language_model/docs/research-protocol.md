# Research protocol

This page describes how the tm_language_model study works: what it is for, the machine on which its recorded runs were made, how its environments are built, and the rules under which runs are made and numbers are reported. Code and documents cite the sections "Project purpose", "Hardware" and "Environment setup" by name and a rule as "protocol rule N". The documents of the study are indexed in [00-README.md](00-README.md). File paths on this page are relative to the study folder.

## Project purpose

The study asks whether a Tsetlin Machine (TM) can be the core of a language model: a token-level TM language model, trained at corpus scale with a subword vocabulary and evaluated as a generative model with a reported likelihood. Prior TM work on language is listed in docs/01, and docs/07 gives the qualified form of the novelty claim. The main model is a sparse event-driven TM engine with readable position-bound literals and sparse signed votes (Track B, docs/03 and docs/11). A masked-position predictor over a shared graph input on the Graph Tsetlin Machine, with an exact Binomial negative-class draw, is kept as the measured reference (Track A). Baselines, heads, decoders, certification and evaluations are written once against a common interface (Track C).

The results aimed at are measured and teacher-free: an output-count scaling curve, masked-token top-1 and top-5, causal perplexity against an in-house Kneser-Ney 5-gram on identical tokens, clause-count and context-length scaling curves, negation robustness against BERT, energy per token, per-token SAT receipts and deterministic replay, together with clause printouts and a concept-dictionary export. Since 2026-09-22 the deliverable is a proof of concept assessed on three pillars whose thresholds are pre-registered in docs/13 (docs/12 F2). P1 is accuracy, against the Kneser-Ney 5-gram, the bigram and CBOW-kNN, and against a from-scratch transformer at equal wall-clock time and equal joules. P2 is reproducibility and extensibility: a bootstrap from a clean checkout, bit-exact replay, a CPU engine and a standalone checker. P3 is scaling with compute: the per-token cost bounds of docs/11 section 10, log-log clause and context curves, a bit-exactness test of clause sharding (docs/11 section 9) and a cost model with measured constants. Next to the engine, the hierarchical package (PyHierarchicalTsetlinMachineCUDA) is to be measured on the paragraph-pair task of the supervisor's project proposal (unpublished), together with layer 1 of the engine and a greedy layer 2 (docs/05 H1 and H2).

Two decisions of 2026-09-24 changed the scope. Rows distilled from a neural teacher are allowed as a separate, pre-registered and labelled family with full energy accounting, while teacher-free rows stay primary (docs/12 F22). The main line of work became self-supervised learning of logical representations with Tsetlin automata, with the language-model likelihood kept as one pillar (docs/12 F23). Nothing of the design is cut (rule 17), and a negative result is reported as negative. These are the aims of the study; what was reached is on the results page ([results.md](results.md)).

## Hardware

The recorded runs of this study were made on one machine, a container with one GPU on a shared host. The items below are [stated: design notes, read-only probe of 2026-09-19]; `make env-check` records the cgroup limits, the GPU name and driver and the nvcc version in `results/<timestamp>_envcheck/`.

- GPU: one Tesla V100-SXM3-32GB with 32 GB of memory (32768 MiB), compute capability 7.0 (sm_70), ECC on. The design is for a single GPU, without bfloat16. Kernels are compiled for `-arch sm_70` into a cubin and not to PTX (`src/tmlm/engine/cuda/build.py`). The toolchain stays on CUDA 12, because CUDA 13 drops Volta.
- CPU: a cgroup quota of 6 CPUs (`cpu.max = 600000 100000`). `nproc` reports a larger number, the core count of the host, which is shared with other workloads. Every thread pool is capped at 6 (`env/env.sh`, `src/tmlm/common/threadcaps.py`), and timings need repeats and a variance.
- Memory: a cgroup limit `memory.max` of 96 GiB and no swap. `free` shows the memory of the host, not the limit. `scripts/mem_guard.py` stops a job at 85 GiB by default.
- Software on the machine: no root access and no system Python, pip, conda, cmake, ninja, numactl or nsys. Present are gcc and g++ 13.3, make, git, curl, nvcc 12.9, nvprof 12.9 and compute-sanitizer. The GPU driver is 570.172.08 (CUDA 12.8). nvprof supports events and metrics up to Volta (docs/12 F12).
- Experiments are sized to fit 32 GB of GPU memory and 85 GiB of host memory.

The environment check of 2026-09-22 recorded these values for the GPU and the limits: GPU name Tesla V100-SXM3-32GB, memory 32768 MiB, driver 570.172.08, `cpu.max` 600000 100000 (a quota of 6 CPUs), `memory.max` 96 GiB, a swap limit of 0, nvcc release 12.9, and 96 as the return value of `os.cpu_count()` [measured: `results/20260922T145432Z_envcheck_clean_copy/envcheck.json`]. The run `20260922T111529Z_envcheck` was made while the container was temporarily attached to a different GPU and is not cited (docs/12 F9).

In the hierarchical package the memory wall is alternatives times concepts, not vocabulary. In the graph substrate the memory of the Tsetlin automata does not depend on the vocabulary, because symbols are encoded as hypervectors [verified in source: memory formulas confirmed, docs/02]. The stock package still has a dense per-class target matrix and a dense per-class update buffer (docs/02, "Blockers in the stock package").

## Environment setup

All commands are relative to the study folder, `studies/tm_language_model/`. From the repository root the make targets are reached with `make -C studies/tm_language_model <target>`. Everything is installed without root access, with `uv`, into virtual environments inside the study folder; the machine of the recorded runs has no system Python.

```
env/bootstrap.sh              # builds .venv-tm and .venv-dl; the make target bootstrap calls it
env/bootstrap.sh --skip-dl    # builds .venv-tm only
env/bootstrap.sh --fresh      # removes both environments first, after the word yes is typed
source env/env.sh             # TMLM_ROOT, CUDA variables, PATH, thread caps, PYTHONHASHSEED
make env-check                # machine limits, GPU, imports, API signatures; writes results/<timestamp>_envcheck/
make configs-check            # experiments/configs/*.json against docs/05, docs/13 and EngineConfig
make lint                     # scripts/check_numbers_have_logs.py over the documents
make test                     # pytest -q tests
make smoke                    # lint, then test
```

`env/bootstrap.sh` is the recipe. It builds two environments with a uv-managed Python 3.11 and refuses to run when `.venv-tm` or `.venv-dl` exists, unless `--fresh` is given. `.venv-tm` holds the Tsetlin stack. numpy, setuptools, wheel, scipy, pytools and mako are installed first, then pycuda is built from source with `--no-build-isolation` against that numpy, then pytest, tmu, cupy, numba, z3-solver, python-sat, codecarbon, nvidia-ml-py, tokenizers, datasets and nltk follow. Last come GraphTsetlinMachine as an editable install of `third_party/GraphTsetlinMachine`, the hierarchical package PyHierarchicalTsetlinMachineCUDA from GitHub at a pinned commit, and this package (`tmlm`) as an editable install. `.venv-dl` holds torch, transformers, accelerate, datasets and spaCy with the model `en_core_web_sm`, for the neural baselines. The two environments are not used in one process; results pass between them through files. If `uv` is not found, the script downloads its standalone installer, and the packages come from PyPI, GitHub and the PyTorch wheel index, so the script needs network access. It checks that the GPU has compute capability 7.0 and that the torch build lists `sm_70`, and it stops when one of the two checks fails. Every command and its output are logged to `results/_bootstrap/<UTC stamp>_bootstrap/bootstrap.log`, with a manifest and the `uv pip freeze` output of both environments next to the log.

`env/htm_install.sh` builds a third environment, `.venv-htm`, for the exploratory pilot of docs/12 F27. It holds the hierarchical package at a later upstream commit, with pycuda, scikit-learn and `tmlm`. The script refuses to run when `.venv-htm` exists and leaves `.venv-tm` unchanged. Like the bootstrap script it checks for a GPU of compute capability 7.0. Its header gives the logged form of the call:

```
scripts/cpu_slot.sh 1 -- .venv-tm/bin/python scripts/run_logged.py --no-gpu-sampler --name htm_env_install \
    --config experiments/cvtm/configs/htm_env_install.json -- bash env/htm_install.sh
```

The lock files in `env/` are freeze records, not inputs. Each script pins its direct dependencies in its own text and, at its end, writes the `uv pip freeze` output of the environment over the lock file: `env/bootstrap.sh` writes `env/tm.lock` and `env/dl.lock`, and `env/htm_install.sh` writes `env/htm.lock`. docs/12 E4 records when `env/tm.lock` and `env/dl.lock` were written; `env/htm.lock` belongs to the pilot environment of docs/12 F27. In the lock files the editable installs are given relative to the study folder (`-e ./third_party/GraphTsetlinMachine` and `-e .`).

| Environment | Built by | Lock file | Main pins in the lock file |

The vendored GraphTsetlinMachine tree is upstream commit c6129e1466d87ebafe411c8a334276ad53c10763 (`third_party/GraphTsetlinMachine/UPSTREAM_COMMIT`). Because its install is editable, `import GraphTsetlinMachine` resolves into `third_party/GraphTsetlinMachine/` itself. That tree is the stock reference and is not edited; patched copies of its kernels live in `src/tmlm/kernels/graphtm_patched/`. tmu is installed from an upstream commit and not from the 0.8.3 wheel, which cannot construct a classifier under NumPy 2 (docs/02 V2, docs/12 A5). torch 2.14.0+cu126 is the last prebuilt torch with sm_70 kernels, so that pin is a ceiling (docs/12 F12).

`env/env.sh` is sourced, not executed, and sourcing it twice changes nothing. It derives `TMLM_ROOT` from its own location, sets the CUDA variables, puts the CUDA binaries on `PATH` and the CUDA libraries on `LD_LIBRARY_PATH`, caps the thread pools of OpenMP, MKL, OpenBLAS, numexpr, numba and rayon at 6 (or at the number of slots that `scripts/cpu_slot.sh` holds), and sets `PYTHONHASHSEED` to 0 unless the caller has set it. The make targets `env-check`, `configs-check`, `lint` and `test` source it and use the interpreter `.venv-tm/bin/python`. `make env-check` runs `scripts/env_check.py` under the shared GPU lock; `make env-check ENV_CHECK_FLAGS=--no-gpu` skips the probes that need a CUDA context. `make smoke` is `lint` followed by `test`, a placeholder for the smoke run that the Makefile describes.

docs/02 V4 and docs/08 call the command block of this section a reconstruction and say that `env/bootstrap.sh` does not exist yet. Both statements are superseded: since 2026-09-22 `env/bootstrap.sh` is the recipe (docs/12 A3 and E4).

Run folders and datasets are not distributed with the repository. The two scripts are written for a machine with a GPU of compute capability 7.0, a CUDA 12 toolkit with nvcc, gcc and g++, and network access; on another GPU they stop at their device check. `make lint` needs the run folders that the documents cite, and the experiments need the datasets, which are obtained separately ([docs/data.md](../../../docs/data.md) at the repository root).

## Rules

The numbering is fixed, because code and documents cite a rule by its number. Four numbers are not used.

1. Costs are measured before anything is built on them. Phase 0 (milestone M1, docs/04) exists to characterise the cost of the stock GraphTsetlinMachine package, among other things its output-count scaling, its profile split and its compile at 16000 outputs, before any kernel is written.
2. Every number in a document or a figure carries an evidence label: measured, derived or unverified. The labels are defined in [00-README.md](00-README.md). A number labelled measured needs a log file under `results/`. In a run folder, `metrics.json` holds each metric as a value with one of these three labels, and the run logger rejects a metrics file that does not have this form: `scripts/run_logged.py` renames it to `metrics_rejected.json` and exits with status 65 when the command itself succeeded. In the documents, `scripts/check_numbers_have_logs.py` (`make lint`) requires every line that carries a `[measured: ...]` label to cite a path under `results/` that exists in the study folder, on the same line or in the same paragraph. It scans `docs/**/*.md` and a `CHANGELOG.md` in the study folder if there is one.
3. A result is claimed only when it is in a log file under `results/`. A target that is missed is reported as a negative result with its log path (docs/13; docs/08, "Positive-by-construction check").
4. Seeds are deterministic. numpy, the Python `random` module and curand are seeded, and every training run and every generated text is required to be reproducible bit for bit (demo G6, deterministic replay). In Track A, `np.random` is seeded before `GraphTsetlinMachine` is imported, because the package seeds curand at import time, and `(seed, grid, block)` is logged. Track B uses a counter-based random number generator only (docs/11 section 3), independent of batch composition, thread layout and launch configuration. `env/env.sh` sets `PYTHONHASHSEED` to 0 unless the caller has set it, so that iteration over sets and dictionaries of strings is the same between runs.
5. Every run is logged to its own folder `results/<UTC timestamp>_<name>/`, written by `scripts/run_logged.py` for an arbitrary command or by `tmlm.common.runlog.RunLog` inside Python. The folder holds `config.json` (the full config), `env.json` (interpreter, package versions, host name, cgroup limits, GPU name and driver), `run.json`, `metrics.json` (each metric with its label), `log.txt` (standard output and standard error) and `MANIFEST.json` (SHA-256 and size of every other file, written last). `run.json` records the start and end time, the wall time, the exit status, `source_tree_hash` (a SHA-256 over the paths and contents of `src/`, `experiments/`, `scripts/`, `tests/` and `env/`, build products excluded), `config_sha256`, `prereg_sha256` (rule 16), the dataset hashes, the command, the thread caps and the peak GPU memory. The peak is the device-wide `memory.used` value of `nvidia-smi`, polled during the run, so it includes other processes on the GPU. `run.json` is written at the start with status `running` and rewritten at the end with status `finished`, so a run that was killed hard stays recognisable. A run folder is created with an exclusive `mkdir` and is not overwritten. The field `git_commit` is filled only when the study folder is itself the root of a git repository with a commit. No commits were made while the study ran (docs/12 A8), so its run records carry no commit id and `source_tree_hash` identifies the code; in the layout of this repository the study folder is not the root of the git repository, so a run started from a clone records no commit id either (see [known limitations](../../../docs/known-limitations.md)).
6. Not used.
7. Every kernel change comes with tests. The exact Binomial negative-class draw has a distributional-equivalence test (docs/02, "Distributional-equivalence test design") that compares the dense negative-class update of the stock kernel with the sparse draw over many seeds. It asserts that the per-clause count of Q-gate selections (drawn negatives) follows Binomial(CLASSES-1, Q/(CLASSES-1)), whose mean is Q. That count is observed with the error gate forced open, because in the stock kernel a negative update needs both gates, the Q gate and the error gate [verified in source: kernels.py:384]. Realised negative updates per clause therefore have mean Q x mean(err/(2T)), about Q/2 at class sums near 0, and not Q [derived]. The wording of the initial design, that the expected per-clause negative updates equal Q, was wrong (docs/12 B15). The stock kernel is the reference: where the test and the kernel disagree, the test is corrected and the kernel is left as it is.
8. Not used.
9. Data under `data/` and run folders under `results/` are kept. The data builders only create files: `write_array` in `src/tmlm/data/corpus_store.py` refuses to overwrite, and a builder that finds an existing file reads it again and checks its recorded SHA-256. A run that is not cited stays on disk as well (docs/12 F9).
10. API facts about the CAIR packages are read from their source or printed from the installed package, and the printout is kept under `results/`. `scripts/env_check.py` (`make env-check`) does this for the classes of `GraphTsetlinMachine.tm`, for `GraphTsetlinMachine.graphs.Graphs`, for `TMAutoEncoder` of tmu and for the classes of `PyHierarchicalTsetlinMachineCUDA.tm`: it writes their `inspect.signature` printouts, together with the cgroup limits and the GPU facts, to `envcheck.json` in a run folder `results/<timestamp>_envcheck/`.
11. Not used.
12. Track A passes `grid=(16*13,1,1)` wherever the stock package takes a grid, because the default grid of the stock package is the H100 setting (docs/02, blocker 4).
13. GPU work is started through `scripts/gpu_run.sh`: `gpu_run.sh shared -- <command>` for training and correctness runs, which may overlap, and `gpu_run.sh exclusive -- <command>` for timing, energy and profiling, which run alone on the GPU. CPU-heavy work is started through `scripts/cpu_slot.sh N -- <command>`, which takes N of 6 slot locks and caps every thread pool at N. Both scripts hold their locks with `flock` on files under `results/.locks`, through file descriptors that the wrapped command inherits, so a lock is released when the command and its children are gone, however they end. New shared jobs queue behind a pending exclusive request, and a long shared run can yield the GPU at a checkpoint (`src/tmlm/common/locks.py`). The wrappers compose, for example `scripts/gpu_run.sh shared -- scripts/mem_guard.py -- scripts/run_logged.py --name e1 --config cfg.json -- python experiments/e1.py`. Since 2026-09-24 a job that needs both kinds of lock takes its CPU slots before the GPU lock, `cpu_slot.sh N -- gpu_run.sh MODE -- ...` (docs/12 F25). At most 3 heavy jobs run at the same time (docs/12 F24).
14. All tuning uses validation data. Every access to a test set is counted: the loaders of a test split call `record_test_access(caller, purpose)` in `src/tmlm/data/evalsets.py`, which appends one JSON line (UTC time, caller, purpose, process id) to `test_access_log.jsonl` under the data root and returns the new count, and which refuses an access without a stated purpose. The count is reported next to the test numbers (docs/13 section 4). A dataset without an official split is counted in the same way, each run that reads it being one access (`docs/notes/preregistration-data-hashes-A6-simlex999.json`). Parser-derived features are an ablation and are computed from masked text only (the leakage rule of docs/06).
15. Not used.
16. The pre-registration `docs/13-preregistration.md` has been frozen since 2026-09-22; changes go only into its dated "Amendments" section. No run that feeds a reported number starts before the file exists. The run logger (`src/tmlm/common/runlog.py`, used by `scripts/run_logged.py`) writes the SHA-256 of the file into every `run.json` as `prereg_sha256`, so each number can be matched to the revision of the file that was in force when its run started. A run config is not a registration: a reading that decides a verdict is fixed in an amendment (docs/13 A9). The copy of the file in this repository carries a publication note that says how its text relates to the registered revisions.
17. Registered measurements are not dropped to save time: time is saved by ordering and by running jobs in parallel (docs/12 F4). The contingency order of docs/04 applies only after a recorded decision.
18. A threshold is not changed to make a result pass, and no result is replaced by a stub or a workaround. A step that fails is recorded as failed, with what failed and why. Every result is reported, positive or negative. In force since 2026-09-22.
