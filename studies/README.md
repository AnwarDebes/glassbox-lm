# Studies

Each study of the programme is one folder in `studies/`. A study keeps its own code, registration, results page and data cards; what spans the studies is in the root [docs](../docs/README.md) folder, and the entry point of the repository is the [root README](../README.md). File paths on this page are written from the repository root.

The status of a study is one of four words. Planned: the study has a folder and a question, and no run has been made. Running: runs are being made or prepared. ## Dependencies between the studies

tm_language_model needs none of the other studies. hierarchical_tm and clause_lm are not self-contained. Both start jobs through scripts and virtual environments of tm_language_model and read data that was built there, and clause_lm also waits on queue files of hierarchical_tm. decision_layer takes only the GPU lock of tm_language_model. tally starts its jobs through the CPU slot and the GPU lock of tm_language_model, runs in environments of tm_language_model and clause_lm, reads data that was built in tm_language_model, and for A2 reads the OR-groups of one run folder of hierarchical_tm. The code finds the other study as a sibling folder, by a relative path that each file derives from its own location, so the study folders have to stay next to each other in `studies/`.

### What follows for a clone

The launchers of hierarchical_tm and clause_lm start `studies/tm_language_model/scripts/mem_guard.py` by name, and those of hierarchical_tm also `studies/tm_language_model/scripts/run_logged.py`. Both scripts begin with `#!/usr/bin/env python3`, so a `python3` with the environment of tm_language_model has to come first on the `PATH` when a launcher is started. The relative paths between the studies replaced absolute ones when the files were prepared for publication, and the replacement was not exercised by a run. The borrowed tools were not moved into a shared place, because that step needs a test run ([known limitations](../docs/known-limitations.md)). The launchers and queue scripts describe one workstation with a single GPU that the studies share through a lock; they record how the jobs were started and are not portable tools.

## Adding a study

A new study is one folder `studies/<short_snake_case_name>/`. It holds a `README.md` that states the question, the status and how the study is run, the folders `src/` and `tests/`, and a folder `docs/` with the registration of the study, its results page and its data cards.

The folders `results/` (run folders) and `data/` (datasets) of a study stay local. The root `.gitignore` ignores `/studies/*/results` and `/studies/*/data`, as it ignores `/studies/*/work`, `/studies/*/references`, `/studies/*/third_party/ref`, every `.venv*` and the run logs of decision_layer and tally, so run folders, datasets, working copies, virtual environments and run logs do not enter the repository. A results page therefore cites a run by its id, exactly as the run folder is named.

The study gets one row in the table at the top of this page and one in the root README: name, question, status and headline result. The status is one of the four words defined above.

Code is shared between studies only when a second study needs it. Until then a new study is self-contained: it reaches no code, data or queue file of another study by path. hierarchical_tm, clause_lm, decision_layer and tally are the exceptions that the previous section describes.

The existing studies differ from this layout in places. tm_language_model has further folders for its experiments, scripts, environments, launch chains and a vendored package. hierarchical_tm keeps its pass rules, `studies/hierarchical_tm/gates.md`, and its hash record, `studies/hierarchical_tm/frozen_settings_hashes.json`, at the study root, because the keys of the hash record are paths relative to that folder, and its two CPU tests are in `studies/hierarchical_tm/src/`. clause_lm has no tests. decision_layer and tally keep their registrations in `registrations/`; next to each frozen one lies its freeze record (`<name>.frozen.json`, written by the study's `scripts/freeze.py`), which holds the UTC time of the freeze and the SHA-256 of the text and of the code. decision_layer also keeps its dev plans and dated notes, with the freeze records of those that were frozen, and its driver scripts in `logs/`, independent recomputations of registered and dev results in `verification/`, and its results in files (JSON files, NumPy archives of predictions and models, and some JSON-lines logs) in `results/confirm/` (registered runs) and `results/explore/` (dev runs), without run folders or run ids.
